## Dependency-license findings

Skyfield 1.55 declares `certifi>=2017.4.17`, `jplephem>=2.13`, `numpy`, and `sgp4>=2.13` in its [release setup file](https://github.com/skyfielders/python-skyfield/blob/1.55/setup.py). [jplephem](https://github.com/brandon-rhodes/python-jplephem/blob/master/LICENSE.txt) and [sgp4](https://github.com/brandon-rhodes/python-sgp4/blob/master/LICENSE) are MIT. [NumPy's main license](https://github.com/numpy/numpy/blob/main/LICENSE.txt) is BSD-3-Clause, but [its build metadata](https://github.com/numpy/numpy/blob/main/pyproject.toml) notes additional bundled-component and wheel-specific licenses; inspect the exact selected Windows wheel before redistribution. [certifi's license file](https://github.com/certifi/python-certifi/blob/master/LICENSE) contains MPL-2.0 terms for its Mozilla-derived CA bundle; file-level notice/source obligations require review if bundled. These licenses are not shown to prohibit a proprietary app, but the exact resolved versions, wheels, hashes, optional features and notices are **not pinned or approved** by this audit.

OpenEphem 0.5.0 [declares](https://github.com/NoahChristian/openephem/blob/main/pyproject.toml) core `skyfield>=1.49` and `numpy>=1.24`, hence Skyfield's dependency tree also applies. Optional extras add `spiceypy`, `timezonefinder`, `geopy`, `tzdata`, and (for `full`) `pandas`; their exact versions, transitive trees, binary components, and licenses have **not** been release-audited. Do not assume `full` is cleared. The project LICENSE also mentions Moshier material and other third-party data; authorship and data terms need file-level inspection. Build-only `hatchling` is not a runtime dependency.

## Ephemeris and auxiliary data: separate rights

Skyfield reads NASA/JPL `.bsp` kernels through jplephem; its MIT license does not license those bytes. [JPL's ephemeris page](https://ssd.jpl.nasa.gov/ephem.html) identifies the DE series; [NAIF's rules](https://naif.jpl.nasa.gov/naif/rules.html) expressly permit use of NAIF-hosted kernels and redistribution **if unmodified**, and permit commercial SPICE use subject to the site's other rules. That is stronger evidence than a generic “public domain” assertion. However, this audit did not acquire any specific DE440/DE440s file, verify that its exact distribution origin is NAIF, inspect its embedded comments, or hash it. For a future release, record the exact official kernel URL, version, checksum, coverage, producer notices, jurisdiction, and whether bundling or hosted use is intended. NAIF warns that kernels from other entities follow those entities' rules; [NASA's science-data policy](https://science.data.nasa.gov/about/license) likewise cautions against assuming one license covers all datasets. No ephemeris data is authorized in this repository by this report.

OpenEphem's own [README](https://github.com/NoahChristian/openephem) identifies DE440, Hipparcos, and optional asteroid kernels as runtime-fetched, not bundled. NAIF's rules can support an **official NAIF-hosted, unmodified** DE kernel after exact-file verification; they do not automatically clear Hipparcos, Horizons-generated asteroid kernels, geocoding/OSM data, or every mirror. Provenance and redistribution terms for each auxiliary dataset remain unresolved. Disable automatic acquisition in any future experiment. Timescale/leap-second/Earth-orientation inputs must also be inventoried and pinned; Skyfield's loader can retrieve data beyond the planet kernel.

## Isolated accuracy and fail-closed validation plan (not run)

1. After separate approval, pin package artifacts/hashes and one official, rights-documented local kernel with coverage and SHA-256. Prohibit network in the process. Use a single explicit local-file loader; reject missing, changed, unsupported, or out-of-range data and any auxiliary timescale dataset without a provenance record. For OpenEphem, inspect and disable download paths and treat **any warning, missing body, partial chart, approximate/Moshier path, or backend substitution as an exception with no chart**; if this cannot be made observable and provable, reject it.
2. Obtain independent synthetic reference cases from a documented observatory/JPL source for tropical geocentric positions, and separately from a documented Jyotisha chart authority for ayanamsha, Lagna, nodes, and divisions. Do not use either library's own outputs as its reference. Record UTC instant (including leap-second handling), WGS84 coordinates/elevation, kernel ID/hash, TT/UT1/ΔT inputs, ecliptic/equinox, apparent versus geometric, geocentric versus topocentric, ayanamsha formula/version, house system and node convention for **both** sides.
3. Compare Sun, Moon and visible planets over ordinary dates, sign/nakshatra/D9 boundaries, leap dates, timezone/DST edges, high latitudes and kernel-span edges. Compute longitude error as `abs(((a - b + 180) % 360) - 180)` degrees; compare Ascendant with the same wrapped metric. Proposed *pilot gates*, to be accepted only after reference uncertainty is known: ≤30 arcseconds for each planetary longitude and ≤60 arcseconds for Ascendant under identical conventions; boundary classifications must match except cases within the documented uncertainty band. Tighter or looser tolerances must be justified from reference uncertainty, not chosen to make a test pass.
4. Record every discrepancy and its source. Test absent/corrupt/wrong-hash kernel, unavailable body/date, blocked outbound access, alternate backend selection, partial OpenEphem results and path redirection. Assert **no chart values** on every failure. No real accuracy test or comparison was run in this audit; OpenEphem's published Swiss-parity figures are not accepted as independent proof.

## Open questions and next decision

1. Which exact NAIF-hosted kernel and auxiliary time data will be approved for local evaluation and potential distribution, under which jurisdiction and notices? A legal reviewer should confirm the planned proprietary deployment against NAIF's conditions rather than equating NASA availability with unrestricted public domain.
2. Can Skyfield be made wholly offline using explicit local files, with exact loaded-kernel identity and no alternate body source? Can OpenEphem expose/guarantee the same and reject its documented graceful degradation?
3. Do the specific Skyfield/OpenEphem wheels include any material not covered by the top-level code licenses? Pin all resolved versions and review their artifact notices; inspect OpenEphem's complete release source, not only README claims.
4. Which ayanamsha, node, house, D9 and Vimshottari conventions are approved, and which independent charts establish their accuracy?

**Recommendation:** investigate Skyfield **first** in a future, explicitly approved isolated phase. Its code license is compatible in principle and the NAIF rules provide a concrete route to a documented kernel; nevertheless, no data or chart calculation is approved now. OpenEphem is second and remains blocked at the fail-closed behavior/source-audit gate. Neither is integrated or authorized for production by this document.
